# ImpulseLock V2 — Detailed Tasks

Granular, checkbox-level breakdown of [roadmap.md](./roadmap.md). Organized by phase, in dependency order. No code is written against this list yet — it's the implementation checklist for when building starts. Each item references the design doc that justifies it, so "why" is always one click away.

## Phase 0 — Foundation: JPA migration + normalized schema ✅ implemented

- [x] Add `flyway-core` + `flyway-mysql` dependencies to `pom.xml` (also swapped `spring-boot-starter-jdbc` for `spring-boot-starter-data-jpa`, and added `spring-security-crypto` for password hashing — see note below).
- [x] Set `spring.jpa.hibernate.ddl-auto=validate` in every profile (never `update`/`create`) — see [database-design.md](./database-design.md). (Only one profile exists as of Phase 0; per-profile split arrives in Phase 6.) Also set `spring.jpa.open-in-view=false`.
- [x] Author `src/main/resources/db/migration/V1__init_schema.sql`: `users`, `roles`, `user_roles`, `restricted_categories`, `transactions`, `rule_configs`, `refresh_tokens`, `audit_log` — full DDL per [database-design.md](./database-design.md). **Deviation**: `transactions.decision_type` / `risk_score` / `explanation` / `triggered_rules` are nullable in this migration, not `NOT NULL` — the JPA entity intentionally doesn't map them yet (see next item), so the DB constraint is loosened until Phase 2 wires the write path and a follow-up migration tightens it.
- [x] Author `V2__seed_roles_and_rule_configs.sql`: seed `ROLE_USER`/`ROLE_ADMIN`, seed `rule_configs` rows with V1-equivalent weights (70/40/30/25/20). **Note**: BLOCK/DELAY decision thresholds (80/40) are *not* seeded anywhere yet — `DecisionEngine` keeps them as hardcoded literals in Phase 0 (unchanged from V1); sourcing them from config is explicit Phase 2 work per this file's own Phase 2 section.
- [x] Create JPA entities: `User`, `Role`, `RestrictedCategory`, `Transaction`, `RuleConfig` (`RefreshToken`, `AuditLog` tables exist in the migration but have no entity yet, per plan). `Transaction` deliberately omits `decisionType`/`riskScore`/`explanation`/`triggeredRules` fields — Phase 0 matches V1's actual behavior (Decision computed and returned, not persisted on the row); Phase 2 adds those fields.
- [x] Add `@EntityListeners(AuditingEntityListener.class)` + `@CreatedDate`/`@LastModifiedDate` fields; enable via `@EnableJpaAuditing` in a `JpaAuditingConfig`.
- [x] Replace `UserRepository`/`TransactionRepository` (hand-written `JdbcTemplate`) with Spring Data JPA interfaces — see [v1/database.md](../v1/database.md) for the code replaced. Also added `RoleRepository`, `RestrictedCategoryRepository`, `RuleConfigRepository` (all needed once entities exist, trivial to add now).
- [x] Add `TransactionSpecifications` (`byUser`, `occurredBetween`, `byCategory`, `byMerchant`, `amountBetween`). **Deviation**: no `byDecisionType` yet — that field isn't mapped on the entity until Phase 2 (see above); a comment in the class marks where it goes.
- [x] Re-point `DecisionEngine`/rules/`TransactionService` at the new entities. `SpendingRule`/`AbstractSpendingRule`/all five rule classes now take `entity.Transaction`/`entity.User` (amount comparisons moved from primitive `double` to `BigDecimal.compareTo`). Old unauthenticated endpoints were kept working, but reshaped: `TransactionEvaluateRequest`/`UserUpsertRequest`/`UserProfileResponse` DTOs (in `dto/`) replace binding directly to `model.Transaction`/`model.UserProfile` (which are deleted — identity moved from a client-chosen `userId` string to a server-generated `id` + unique `username`, so byte-for-byte contract preservation wasn't possible or desirable). A new transitional `UserService` hashes passwords (`spring-security-crypto`'s `BCryptPasswordEncoder`) and seeds a default `"LUXURY"` restricted-category row per new user, replacing `CategoryRestrictionRule`'s old hardcoded fallback now that the association is a real child table. Also removed `ImpulseLockApplication`'s leftover startup demo block (see [v1/design-decisions.md](../v1/design-decisions.md) item 9) since it directly `new`-ed up the now-deleted model classes.
- [x] Repository-level tests: Testcontainers MySQL (`AbstractIntegrationTest` base class using `@ServiceConnection`), covering unique constraints (`username`, `email`), cascade delete (`restricted_categories`), auditing timestamps, and `TransactionSpecifications` filtering. **Not run in this environment** (no Docker available here) — verified to compile; needs a Docker-capable machine or CI to actually execute (see [deployment-plan.md](./deployment-plan.md)).
- [x] Verify: same transaction inputs produce the same `Decision` output as documented in [v1/rule-engine.md](../v1/rule-engine.md) — `DecisionEngineTest` and per-rule boundary tests (fire/no-fire at the exact threshold) added and passing; confirms the persistence swap didn't change rule/engine behavior (including V1's uncapped-above-100 quirk, deliberately preserved until Phase 2).

## Phase 1 — Security: JWT auth, Spring Security, RBAC ✅ implemented

- [x] Add `spring-boot-starter-security` + a JWT library to `pom.xml`. Used `io.jsonwebtoken` (jjwt) 0.12.6 (`jjwt-api`/`jjwt-impl`/`jjwt-jackson`) over Nimbus - smaller surface for the simple "sign and verify HS256" need here. Also added `spring-boot-webmvc-test` (test scope): Spring Boot 4 moved `@AutoConfigureMockMvc`/`@WebMvcTest` out of `spring-boot-test-autoconfigure` into this new module as part of its web-stack split - not anticipated when this checklist was written.
- [x] `User` entity already had `passwordHash`/`enabled`/roles from Phase 0; no change needed here.
- [x] `SecurityUser` (implements `UserDetails`, wraps `User`) + `SecurityUserDetailsService` (implements `UserDetailsService`, loads by username via `UserRepository`).
- [x] `JwtService`: `generateAccessToken(User)`, `getAccessTokenTtlSeconds()`, `parseClaims(token)` / `extractUsername(token)` (both return `Optional`, empty on any parse/verify failure). **Deviation**: no separate `generateRefreshToken()` on this class - refresh-token generation/hashing lives entirely in `RefreshTokenService` instead, since the design treats access tokens (JWT) and refresh tokens (opaque random) as different concerns end to end.
- [x] `JwtAuthenticationFilter` (`OncePerRequestFilter`): reads `Authorization: Bearer`, resolves username via `JwtService`, then always re-loads a fresh `SecurityUser` from the DB (via `SecurityUserDetailsService`) rather than trusting an embedded roles claim - so a role change or account-disable takes effect on the very next request, not only after the access token expires. Swallows expired/tampered/unknown-user tokens (leaves the request unauthenticated) rather than throwing.
- [x] `RefreshToken` entity + `RefreshTokenRepository`; `RefreshTokenService`: `issue`/`rotate`/`revoke`/`revokeAllForUser`, SHA-256 hash only ever persisted.
- [x] `SecurityConfig`: stateless session policy, CSRF disabled (reasoning in the class javadoc), `/api/v2/auth/**` permitAll, `/api/v2/admin/**` → `hasRole("ADMIN")`, everything else → authenticated. `BCryptPasswordEncoder` bean already existed from Phase 0 (`PasswordEncoderConfig`) and is picked up automatically by Spring Security's zero-config `DaoAuthenticationProvider` wiring alongside the single `UserDetailsService` bean. **Note**: the `/api/v2/admin/**` rule protects a URL pattern only - no admin controller exists until Phase 3, so it 404s past the security gate for an admin caller (see `AuthIntegrationTest`); it exists now purely so the 403 path is testable in Phase 1.
- [x] `RestAuthenticationEntryPoint` (401 JSON) + `RestAccessDeniedHandler` (403 JSON), both delegating to a shared `SecurityErrorResponseWriter` — matching [api-design.md](./api-design.md#error-format).
- [x] `AuthController` + `AuthService`: `register`/`login`/`refresh`/`logout`, at `/api/v2/auth` (placed directly at the target V2 path since there's no legacy endpoint to preserve, unlike `/transaction` and `/users`). DTOs (`RegisterRequest`, `LoginRequest`, `AuthResponse`) created without Bean Validation annotations, as planned - Phase 4 adds those. Also added `UserAlreadyExistsException` (409) and a generic `AuthenticationException` handler (401, generic "Invalid username or password" message) to `GlobalExceptionHandler` - pulled forward from Phase 4's fuller matrix out of necessity, since login needed *some* correct status code now.
- [x] Refresh-token cookie: httpOnly/`Secure`/`SameSite=Strict`, path scoped to `/api/v2/auth` only, set on register/login/refresh, cleared (maxAge 0) on logout.
- [x] `CorsConfig` rewritten as a `CorsConfigurationSource` bean (not `WebMvcConfigurer`) reading `app.cors.allowed-origins`; `allowCredentials(true)` added since the refresh-token cookie now needs it.
- [x] Retrofitted `TransactionController`/`UserController`: both now take `@AuthenticationPrincipal SecurityUser` and pass the username down to the service layer, which re-fetches the `User` fresh inside its own `@Transactional` method (rather than reusing the detached entity from the filter's already-closed transaction, which would throw `LazyInitializationException` on `restrictedCategories`). `TransactionEvaluateRequest` and the old `UserUpsertRequest` (deleted, replaced by `UserPreferencesUpdateRequest`) no longer carry any user-identifier field - closes [v1/design-decisions.md](../v1/design-decisions.md) item 7. `UserController`'s single endpoint was also renamed `POST /users` → `PUT /users/me/preferences` and now only updates preferences (account creation moved exclusively to `/auth/register`) - a small, necessary reshaping since letting an unauthenticated endpoint create arbitrary accounts once real auth exists would be a security hole.
- [x] Security integration tests (`AuthIntegrationTest`, MockMvc against the real filter chain, not `@WebMvcTest` with security sliced out): register/duplicate-username/login/wrong-password, protected-endpoint with no/valid/tampered token, refresh with missing cookie, refresh rotation invalidating the previous token, logout revocation, and wrong-role vs admin-role against the `/api/v2/admin/**` rule. **Deviation**: "expire→refresh" is tested via rotation-invalidates-the-old-token instead of actually waiting out the access-token TTL - deterministic and exercises the same rotation mechanism without manipulating time in a test. **Not run in this environment** (no Docker available here, same as Phase 0's repository tests) - verified to compile; needs a Docker-capable machine or CI to actually execute.

## Phase 2 — Domain improvements: configurable rules, real daily-limit/frequency logic ✅ implemented

- [x] `RuleConfig` entity + `RuleConfigRepository` already existed from Phase 0; added the service layer now (`RuleConfigService`: `findAll`, `findAllByCode`, `getByCode`, `update`).
- [x] `RuleConfigService.update` exists but no admin controller calls it yet - wiring is still Phase 3, as planned.
- [x] Refactored `SpendingRule`/`AbstractSpendingRule` to a `RuleContext`-based design rather than threading a single `RuleConfig` through the existing signature: `evaluate(Transaction, User, RuleContext)`. `RuleContext` (new, in `engine/`) bundles the resolved weight/enabled/params for *every* rule plus a shared 24-hour lookback of the user's own transactions, built once per evaluation by a new `RuleContextFactory` (one `rule_configs` query, one `decision_thresholds` query, one transaction-history query - not one query per rule). This keeps rules as pure, dependency-free, easily unit-testable classes (construct a `RuleContext` fixture by hand, no Spring/mocks needed) rather than turning them into Spring beans with injected repositories. `AbstractSpendingRule` now takes `(ruleCode, explanation)` instead of `(weight, explanation)`; weight/params are resolved per-call via `context.weightFor(ruleCode)`/`context.paramsFor(ruleCode)`. `RuleEngineConfig`'s bean wiring is unchanged - this was a real test of whether the Strategy-pattern DI design from V1 would survive becoming config-driven, and it did.
- [x] `HighAmountRule` → calendar-day total (midnight-to-midnight in server time, not a rolling 24h window - documented choice, in the class javadoc, matching how consumer banking apps usually describe a "daily limit"). Sums the user's same-day transactions from `RuleContext.getRecentTransactions()` (filtered in-memory, not a dedicated SQL aggregate query - the shared 24h fetch already contains everything needed) plus the current transaction, compares to `dailyLimit`.
- [x] `FrequentTransactionRule` → real velocity check: counts transactions within `params.velocityWindowMinutes` of the transaction being evaluated (not wall-clock "now" - deterministic/testable), fires at `params.velocityCountThreshold` (including the current transaction).
- [x] `NightSpendingRule`: `nightStartHour`/`nightEndHour` now read from `RuleConfig.params` (defaults 23/6 match V1 exactly if a row's params are absent).
- [x] `SensitivityLevelRule`: `sensitivityThreshold` now read from `RuleConfig.params` (default 8).
- [x] `CategoryRestrictionRule`/registration-seeding: **already done in Phase 0/1** - the hardcoded "LUXURY" fallback was removed when `restricted_categories` became a child table (Phase 0), and `AuthService`/`UserService.registerNewUser` already seeds a default `"LUXURY"` row per new user (Phase 1). Nothing left to do here; noting it so this checklist reflects reality.
- [x] `DecisionEngine`: caps the *reported* risk score at 100 (`Math.min(totalRisk, 100)`) but still compares the **uncapped** total against the thresholds for the BLOCK/DELAY decision (capping only changes what's displayed, never the outcome - a transaction scoring 140 and one scoring 80 both correctly BLOCK). Thresholds now come from a new `decision_thresholds` table/`DecisionThresholds` entity (a dedicated table, not two rows folded into `rule_configs`, since a threshold isn't "a rule" - see `V3__add_decision_thresholds.sql`), seeded with V1's exact 80/40.
- [x] `Transaction` entity: added `decisionType`/`riskScore`/`explanation`/`triggeredRules` fields; `TransactionService` now populates all four from the computed `Decision` before saving (V1/Phase 0/1 only ever returned the Decision to the caller - see [v1/database.md](../v1/database.md)). `triggeredRules` is a new `List<TriggeredRuleEntry>` (record: ruleCode/weight/message), persisted via a dedicated `TriggeredRulesConverter`, and reused as-is on the `Decision` API response (structured alternative to parsing the semicolon-joined `explanation` string - see [v1/rule-engine.md](../v1/rule-engine.md)). **Migration note**: `V4__tighten_transaction_decision_columns.sql` backfills any nulls then tightens these four columns to `NOT NULL`, and moves `decision_type` from MySQL `ENUM` to `VARCHAR(10) CHECK (...)` - safer under Hibernate's `ddl-auto=validate` than relying on exact ENUM/JDBC-type-code matching across driver versions. `V5__update_frequent_transaction_rule_params.sql` replaces Phase 0's placeholder `amountThreshold` seed param with the real `velocityWindowMinutes`/`velocityCountThreshold` the rule now reads.
- [x] Unit tests per rule at exact fire/no-fire boundaries, now including the configurable-params paths (custom night window, custom velocity window/threshold, custom sensitivity threshold) and calendar-day aggregation/isolation for `HighAmountRule`; `DecisionEngineTest` covers the 100-point cap, disabled-rule skipping, and threshold boundaries. `RuleConfigServiceTest` (Mockito) added for the new service. `RuleConfigRepositoryTest` extended to check the updated `FREQUENT_TRANSACTION` params; new `DecisionThresholdsRepositoryTest` checks the seeded 80/40. 30 Docker-independent tests pass locally (`mvn test -Dtest=...`); the Testcontainers-backed repository/integration tests are unchanged in nature from Phase 0/1 (still not run in this environment - no local Docker).

## Phase 3 — API surface: advanced transaction history, dashboard, admin endpoints ✅ implemented

- [x] `TransactionController` moved from the legacy `/transaction` path to `/api/v2/transactions`: `POST /evaluate`, `GET /{publicId}` (owner or `ROLE_ADMIN` only - a non-owner gets the same `TransactionNotFoundException` → 404 an unknown `publicId` would, never 403, per [api-design.md](./api-design.md#error-format)). `evaluateAndSave` now returns the saved `Transaction` entity itself (not a bare `Decision`) so evaluate/get-by-id/history all map through the same `TransactionMapper`.
- [x] `GET /api/v2/transactions/history`: pagination via Spring Data's auto-resolved `Pageable` (`page`/`size`/`sort` query params, no manual parsing needed), filters (`from`, `to`, `category`, `merchant`, `decisionType`, `minAmount`, `maxAmount`) via `TransactionSpecifications` - including a new `byDecisionType` builder, which Phase 0 had explicitly deferred until `Transaction.decisionType` existed (Phase 2 added it).
- [x] `GET /api/v2/transactions/history/export`: `StreamingResponseBody` CSV (not buffered in memory), capped at 10,000 rows, manually quote/escaped. **Deviation**: not yet audit-logged as a data-export action - the audit writer is Phase 4 work (noted inline in the controller).
- [x] `UserController` moved from `/users` to `/api/v2/users`, split into `GET /me`, `PUT /me/preferences`, `GET/POST/DELETE /me/restricted-categories`.
- [x] `DashboardController` + `DashboardService`: `summary`, `spending-by-category`, `risk-trend`, `top-triggered-rules`, each scoped to the caller by default with an optional `userId` param for `ROLE_ADMIN` cross-user viewing (checked in the service, throwing Spring Security's `AccessDeniedException` directly for a non-admin - no new exception handler needed, it already flows to `RestAccessDeniedHandler` from Phase 1). Aggregates are computed in-memory over one fetched 30-day transaction list per call (consistent with `RuleContextFactory`'s established pattern), not via separate SQL aggregate queries. **Deviation**: the admin cross-user override works but isn't audit-logged yet, same reason as the CSV export.
- [x] `AdminUserController`: `GET /users` (paginated), `GET /users/{id}`, `PATCH /users/{id}/status` - via a new `AdminUserService`, kept separate from `UserService` (which only ever acts on the caller's own account).
- [x] `AdminRuleConfigController`: `GET /rule-configs`, `PUT /rule-configs/{ruleCode}` - the first real caller of Phase 2's `RuleConfigService.update`.
- [x] `AdminAuditLogController`: `GET /audit-logs` with `action`/`from`/`to` filters and pagination, backed by a new `AuditLog` entity/repository/`AuditLogSpecifications` and a read-only `AuditLogService`. Endpoint shell as planned - returns real (currently empty) paginated results; nothing writes to `audit_log` until Phase 4's `@Auditable` aspect.
- [x] `PageResponseDto<T>` with a `from(Page<S>, Function<S,T>)` factory, used by every paginated endpoint above.
- [x] Added MapStruct (`mapstruct` + `mapstruct-processor` via the compiler plugin's `annotationProcessorPaths`) and wrote `TransactionMapper`, `RuleConfigMapper`, `AuditLogMapper` for the three entities with a genuine entity→DTO shape translation introduced this phase. Dashboard DTOs are aggregation results (not direct entity mappings) and `UserProfileResponse` predates this phase, so neither uses MapStruct - a deliberate scope reading of "every entity↔DTO pair introduced this phase," not an oversight.
- [x] Controller integration tests (MockMvc + real security chain, `@SpringBootTest` not `@WebMvcTest`): `TransactionControllerIntegrationTest`, `UserControllerIntegrationTest`, `DashboardControllerIntegrationTest`, `AdminControllerIntegrationTest` (covering all three admin controllers together, since they share setup boilerplate). Fixture transactions use a fixed daytime `occurredAt` throughout to avoid `NightSpendingRule` non-deterministically firing depending on wall-clock test-run time. **Not run in this environment** (no Docker available here, same as every Testcontainers-backed test since Phase 0) - verified to compile; needs a Docker-capable machine or CI to actually execute.
